Replaced the fully-autogenerated `sidebars.ts` (`{type:'autogenerated', dirName:'.'}`)
with a manually-authored tree, per user request: the flat 16-bible x
15-19-section list was "hard to read and spot." Each bible now nests its
existing numbered folders under concept-based categories (e.g. CSS: 🌱
Fundamentals / 📐 Layout Systems / 🎨 Typography, Color & Theming / 🎬 Motion,
Forms & Interaction / ♿ Accessibility & I18n / ⚡ Performance & Architecture /
🍳 Production Patterns & Recipes). No files were moved and no links changed -
each leaf category still points at `{type:'autogenerated', dirName:'<bible>/<folder>'}`,
so an existing folder's docs are picked up automatically even if new files
are added inside it later.

Also added `@easyops-cn/docusaurus-search-local` (self-hosted, offline index
built at `yarn build` time into `search-index.json`) since this is a static
GitHub Pages site with no backend for Algolia-style hosted search - confirmed
with the user (chose local search over applying for Algolia DocSearch).
Configured in `docusaurus.config.ts` `plugins: [...]`.

**Why:** User found the single giant per-bible sidebar list hard to navigate
and asked for both concept-based grouping (Fundamentals/Customization/Theming/etc.)
and global search, across all 16 bibles in one pass (not staged one bible at
a time).

**How to apply:**
- The category taxonomy per bible lives only in `sidebars.ts` now - if you add
  a **new top-level numbered folder** to a bible (not just a new file inside
  an existing folder), you must add a `{type:'autogenerated', dirName:...}`
  entry for it under the right category by hand, or it silently won't appear
  in the sidebar at all (manual sidebars don't auto-include new directories).
  New *files* inside an already-referenced folder need no sidebar change.
- Search index regenerates on every `yarn build` automatically - no separate
  step needed.
- A generator script (`scripts` folder does not have this - it was a one-off
  temp script in the scratchpad, not committed) built `sidebars.ts` from a
  taxonomy table; if the whole thing needs regenerating from scratch later,
  rebuild the same per-bible group tables rather than hand-editing 236 leaf
  entries.
