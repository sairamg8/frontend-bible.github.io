                      THE ULTIMATE ESLINT & OXLINT BIBLE

DOCUMENTATION STANDARD FOR EVERY CONCEPT:
Each concept must be documented with 4 mandatory sections:
  1. Concept & Under-the-Hood Mechanics (parser/AST, rule pipeline, config merge)
  2. Real-World Engineering Scenario (Production Use Case)
  3. Production-Grade Code Example (flat config / .oxlintrc / CLI as appropriate)
  4. Senior Engineer Edge Cases & Pitfalls (false positives, perf cliffs, monorepos)

NOTE: This bible catalogs *lint tooling* (ESLint + Oxlint): architecture, config,
rules, plugins, type-aware analysis, migration, and running both together.
Formatting (Prettier/Oxfmt/Biome format) is mentioned only at the lint/format
boundary - do not turn this into a formatter bible. Project-structure / CI
decision context may cross-link `frontend_architecture_bible_syllabus.txt`
SECTION 12 (CI/CD) and SECTION 15 (team practices) where relevant.

SCOPE SNAPSHOT (as of 2026):
  - ESLint: flat config is the only supported path for modern versions; legacy
    `.eslintrc*` is migration history. Cover ESLint 9+ APIs (`defineConfig`,
    `globalIgnores`, `extends` in flat config) and note major version EOL when
    documenting upgrade paths.
  - Oxlint: Oxc-based Rust linter, ~50-100x faster than ESLint on large trees,
    800+ rules, native plugin reimplementations, type-aware via tsgolint/tsgo,
    JS plugins still alpha. Primary config: `.oxlintrc.json` or `oxlint.config.ts`.
  - Coexistence is first-class: many production monorepos run `oxlint && eslint`
    with `eslint-plugin-oxlint` disabling overlapping rules.

SECTION 1: LINTING LANDSCAPE & TOOLING DECISIONS
--------------------------------------------------------------------------------
1.1 Why Lint at All
    - Static analysis vs tests vs types     - What linting catches that tsc and unit tests do not (bug patterns, a11y, hooks rules, import graphs).
    - Signal vs noise                            - Correctness-first defaults vs style nits; why noisy rules destroy adoption.
    - Lint in the feedback loop                     - Editor -> pre-commit -> CI ordering and the cost of slow lint on PR velocity.

1.2 Choosing a Linter (Decision Tree)
    - ESLint-only                              - Need full custom rules, obscure plugins, or edge-case plugin APIs Oxlint cannot run yet.
    - Oxlint-only                                 - Greenfield or greenfield-like apps; ruleset covered by native plugins; CI time is a bottleneck.
    - Oxlint + ESLint coexistence                    - Large legacy trees: fast path for most rules, ESLint retained for gaps (recommended large-repo path).
    - Biome / other all-in-one tools                    - Integrated format+lint tradeoff; when a dedicated linter + separate formatter wins instead.
    - Vite+ / unified toolchains                           - When the team wants Oxlint+Oxfmt inside a broader toolchain vs bare oxlint package.

1.3 Lint vs Format Boundary
    - Rules that rewrite style                 - Why stylistic ESLint rules conflict with Prettier; eslint-config-prettier / stylistic plugin split.
    - Oxfmt / Prettier / Biome format             - Formatters own whitespace/quotes; linters own correctness and API misuse.
    - Single source of truth for style               - Pick one formatter; disable overlapping lint style rules to end PR bikesheds.

SECTION 2: ESLINT CORE ARCHITECTURE
--------------------------------------------------------------------------------
2.1 How ESLint Works Under the Hood
    - Source -> parse -> AST -> rules           - Pipeline: file read, parser produces ESTree (or compatible) AST, rules visit nodes, reports/fixes collected.
    - ESTree & parser role                         - Default Espree for JS; swap parser for TypeScript/Vue/etc. via languageOptions.parser.
    - Rule visitor pattern                            - Selectors / node-type visitors; enter/exit; why AST shape knowledge matters for custom rules.
    - Linter vs CLI vs IDE                              - Same core engine; CLI batches files + formatters; editors lint on change with subset of options.
    - Autofix model                                        - Fix objects with range+text; multipass fixing; conflicts when two rules fix the same span.

2.2 Legacy Config Era (Historical Context)
    - .eslintrc.* formats                      - JSON/YAML/JS cascaded configs; `extends`, `overrides`, `env`, `globals`.
    - .eslintignore                               - Separate ignore file; superseded by flat `ignores` / `globalIgnores`.
    - Why flat config replaced cascading             - Implicit directory cascade was hard to reason about; flat is explicit arrays of config objects.
    - When you still see eslintrc                       - Older monorepo packages, generate-era Next templates; migrate before depending on new APIs.

SECTION 3: ESLINT FLAT CONFIG (MODERN DEFAULT)
--------------------------------------------------------------------------------
3.1 Config File Forms
    - eslint.config.js / .mjs / .cjs           - ESM vs CJS export default; package `"type": "module"` implications.
    - eslint.config.ts                            - Type-safe config (supported in modern ESLint); tooling/runtime requirements.
    - defineConfig() from eslint/config              - Helper for typed configs, better IntelliSense, and evolving flat-config ergonomics.
    - Config as an array of objects                     - Each object can set files, ignores, languageOptions, plugins, rules, settings.

3.2 Core Flat-Config Object Fields
    - files / ignores                          - Glob targeting; config objects only apply to matched files.
    - globalIgnores()                             - Repo-wide ignores without accidentally creating a global block that disables other configs.
    - languageOptions                              - parser, parserOptions, globals, ecmaVersion, sourceType (module/script/commonjs).
    - plugins                                        - Map of plugin name -> plugin object (no magic string resolution like legacy).
    - rules                                            - Rule id -> severity | [severity, ...options].
    - settings                                          - Shared plugin settings (e.g. react.version, import resolvers).
    - linterOptions                                    - reportUnusedDisableDirectives, noInlineConfig, etc.
    - processor                                          - Multi-part files (e.g. Vue/Markdown code blocks) extraction before lint.

3.3 Composition: extends, Cascading, and Shareable Configs
    - extends in flat config                   - Modern ergonomic composition (configs as imported objects/arrays).
    - Spreading recommended configs               - @eslint/js, typescript-eslint, plugin.configs.recommended patterns.
    - Order and override semantics                   - Later array entries win for same file+rule; how to intentionally override.
    - FlatCompat / @eslint/eslintrc                     - Bridging old `extends: 'plugin:X/recommended'` strings during migration.
    - Config Inspector                                 - Visualizing which config object applies which rules to a file.

SECTION 12: OXLINT CORE ARCHITECTURE
--------------------------------------------------------------------------------
12.1 What Oxlint Is
    - Oxc compiler stack                       - Shared parser/semantic analysis with other Oxc tools; Rust performance.
    - Design goals                                - Large repos, CI throughput, high-signal correctness defaults, ESLint migration path.
    - Benchmark mental model                         - Order-of-magnitude speedups (often cited ~50-100x) and what workloads show them.
    - Language support                                - JS/TS/JSX/TSX; framework files (Vue/Svelte/Astro) via script-block linting.

12.2 Architectural Differences from ESLint
    - Native rules vs JS plugin host           - Most rules implemented in Rust; optional JS plugin bridge (alpha).
    - Category-based defaults                     - correctness-first enablement vs ESLint recommended packages.
    - Config shape heritage                          - `.oxlintrc.json` aligned with ESLint v8-style schema (not ESLint flat array).
    - Multi-file analysis as first-class            - Project module graph for import/cycle class rules without ESLint's classic cliff.

SECTION 18: COEXISTENCE - ESLINT + OXLINT IN ONE REPO
--------------------------------------------------------------------------------
18.1 Recommended Dual-Run Pattern
    - oxlint && eslint                         - Fast fail first; ESLint for residual rules.
    - eslint-plugin-oxlint                        - Disables ESLint rules already covered by Oxlint to avoid double work/noise.
    - Rule ownership matrix                          - Document which tool owns which concern (hooks, import cycles, a11y, custom).
    - Script layout                                     - lint:ox, lint:eslint, lint (aggregate); CI job structuring.

18.2 Overlap & Conflict Management
    - Duplicate diagnostics                    - Same bug reported twice confuses authors; disable overlap on one side.
    - Severity alignment                          - error in one tool + warn in the other is worse than a single owner.
    - Disable comment dual support                   - Prefer one comment dialect long-term; respect both during transition.
    - IDE extensions                                 - Running both language services; performance on large files.

18.3 When to Drop ESLint Entirely
    - Coverage checklist                       - Custom rules ported or replaced; plugin gaps closed; team training done.
    - Small/medium vs large repos                 - Official guidance nuance: full replace vs incremental.
    - Rollback plan                                  - Keep ESLint config in git history / feature flag scripts temporarily.

SECTION 19: MIGRATION PATHS
--------------------------------------------------------------------------------
19.1 ESLint Legacy -> Flat Config
    - @eslint/migrate-config                   - Mechanical conversion from .eslintrc.
    - FlatCompat for stubborn extends             - Temporary bridges for unmigrated shareable configs.
    - Peer dep & plugin flat exports                 - Updating Next/React/TS ecosystems to flat-native configs.
    - Editor + CI cutover day                           - Extension settings, cache clear, required checks.

19.2 ESLint -> Oxlint
    - @oxlint/migrate                          - Convert flat ESLint config to .oxlintrc.json; report unsupported rules.
    - Reviewing migration output                  - Severity/options preservation; manual gap list.
    - Moving ignores into ignorePatterns             - Stop relying on .eslintignore long-term.
    - Replacing biome-ignore / other dialects           - Map to eslint-disable or oxlint-disable consistently.

19.3 Dual-Stack Migration (Large Monorepos)
    - Phase 1: add Oxlint correctness          - No rule deletions in ESLint yet.
    - Phase 2: eslint-plugin-oxlint               - Turn off overlaps; measure CI time.
    - Phase 3: expand Oxlint categories/plugins      - Delete dead ESLint plugins as coverage lands.
    - Phase 4: optional ESLint removal                  - Only when residual rule set is empty or accepted as debt.

SECTION 20: CI, MONOREPOS & PERFORMANCE ENGINEERING
--------------------------------------------------------------------------------
20.1 CI Design for Linters
    - Fail fast with Oxlint                    - Short job before expensive test/e2e matrices.
    - Caching strategy                            - ESLint --cache; Oxlint native speed reduces cache need but still cache deps.
    - Sharding and path filters                      - Monorepo affected-package lint vs always-full-tree.
    - Required checks & warning budgets                 - max-warnings, deny-warnings policies.
    - SARIF / code scanning integration                    - eslint-formatter-sarif for GitHub Security tab; surfacing lint as scanning alerts, not just job failures.
    - CI annotations                                          - GitHub Actions problem matchers / -f json piping so lint errors inline on the diff.

20.2 Monorepo Patterns
    - Root config + package overrides          - Shared baseline with package-level overrides for apps/libs.
    - Per-package ESLint flat configs             - vs single root flat config with files globs.
    - Oxlint nearest-config layout                   - Package-local .oxlintrc for divergent apps.
    - Task runners (Turbo/Nx)                           - lint task graph, remote cache invalidation on config change.

20.3 Performance Pitfalls
    - Type-aware cost on ESLint                - projectService tuning; limiting type-aware to src not scripts.
    - import plugin resolvers                     - Expensive resolution; prefer Oxlint multi-file for cycle checks when possible.
    - JS plugins count in Oxlint                     - Known slowdowns with many concurrent JS plugins; keep alpha plugins few.
    - Over-broad globs                               - Linting node_modules/dist by accident.
