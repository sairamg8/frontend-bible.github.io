================================================================================
                        THE ULTIMATE FRONTEND ARCHITECTURE BIBLE
        Complete Master Syllabus for Real-World Project Structure & Decisions
================================================================================
Note: Unlike the other bibles in this collection (which catalog APIs), this one
catalogs DECISIONS - the tradeoffs you actually face building/scaling a real app.

--------------------------------------------------------------------------------
SECTION 1: PROJECT STRUCTURE & ORGANIZATION
--------------------------------------------------------------------------------
1.1 Folder Strategy
    - Feature-based ("colocation")          - Group by domain (features/checkout/*) not by file type; scales better than type-based folders.
    - Layer-based (components/hooks/utils)     - Simpler for small apps, breaks down past ~20-30 features (cross-cutting imports everywhere).
    - Colocation principle                        - Tests, styles, and types live next to the component that owns them, not in parallel mirrored trees.
    - Barrel files (index.ts re-exports)             - Convenience vs the tree-shaking/circular-import costs they introduce at scale.


--------------------------------------------------------------------------------
SECTION 2: COMPONENT ARCHITECTURE
--------------------------------------------------------------------------------
2.1 Composition Patterns
    - Atomic Design (atoms/molecules/organisms) - Useful as a mental model for a design system, rarely enforced as literal folders in practice.
    - Container/Presentational split               - Mostly obsolete since hooks; data-fetching and rendering concerns now separate via custom hooks instead of component layers.
    - Compound components                             - Parent manages shared state, children consume via context (<Select><Select.Option/></Select>) - flexible public APIs for libraries/design systems.
    - Headless components                               - Logic/behavior with zero styling opinion (Radix/Headless UI pattern), letting consumers own all visual decisions.
    - Composition over inheritance                        - Slots/children props over configuration-prop explosion for variant handling.


--------------------------------------------------------------------------------
SECTION 3: STATE MANAGEMENT DECISION TREE
--------------------------------------------------------------------------------
3.1 Choosing the Right Tool
    - Local state (useState/useReducer)        - Default choice; state used by one component and its direct children.
    - Lifted/shared state (Context)               - Low-frequency updates shared across a subtree (theme, auth user) - NOT for high-frequency data (causes broad re-renders).
    - Global client state (Zustand/Redux Toolkit) - Cross-cutting UI state needed app-wide, complex mutation logic, or when Redux DevTools/time-travel is valuable.
    - Server state (TanStack Query/RTK Query)       - Anything fetched from an API - treat it as a cache with staleness, not as state you own; do not duplicate it into a global store.
    - The core rule                                    - Colocate state as close as possible to where it's used; lift only when genuinely shared.


--------------------------------------------------------------------------------
SECTION 4: DATA LAYER & API ARCHITECTURE
--------------------------------------------------------------------------------
4.1 Structuring the Data Boundary
    - BFF (Backend-for-Frontend) pattern       - A thin server layer shaping/aggregating backend calls specifically for this frontend's needs.
    - API client abstraction                      - One typed client module wrapping fetch/axios so auth headers, error shape, and base URL live in one place.
    - Generated types                                - OpenAPI/GraphQL codegen producing types+hooks from a schema, eliminating hand-written request/response types drifting from reality.
    - Standardized error/loading contracts             - A consistent { data, error, isLoading } shape so every screen handles the same three states the same way.


--------------------------------------------------------------------------------
SECTION 5: ROUTING & NAVIGATION ARCHITECTURE
--------------------------------------------------------------------------------
5.1 Real-World Routing Concerns
    - Nested layouts                          - Shared chrome (nav/sidebar) persisting across child route transitions without remounting.
    - Route-based code splitting                 - Default splitting boundary for most apps; the biggest win-per-effort for bundle size.
    - Auth-gated routes                             - Guard patterns (redirect-on-mount vs middleware-level) and the flash-of-unauthenticated-content problem.
    - Deep linking & URL as state                     - Encoding filters/pagination/tabs in the URL (searchParams) so state survives refresh/sharing.


--------------------------------------------------------------------------------
SECTION 6: STYLING ARCHITECTURE
--------------------------------------------------------------------------------
6.1 Choosing & Scaling a Styling Approach
    - Utility-first (Tailwind)                - Fast iteration, no naming decisions, but markup verbosity and a learning curve for design consistency.
    - CSS-in-JS (styled-components/Emotion)      - Colocated styles, dynamic theming, but runtime cost and SSR complexity (mostly losing ground to zero-runtime alternatives).
    - CSS Modules                                  - Scoped by default, zero runtime cost, pairs well with design tokens; less dynamic than CSS-in-JS.
    - Design tokens                                  - Single source of truth for color/spacing/typography consumed by both code and design tools (Figma).
    - Theming strategy                                 - CSS custom properties for runtime theme switching (dark mode) vs build-time theme variants.
    - Fullstack color strategy                         - Tokens as CSS vars + Tailwind/Modules delivery; avoid hex-in-components and runtime CSS-in-JS as the global color system.


--------------------------------------------------------------------------------
SECTION 7: MONOREPO & MULTI-APP STRATEGY
--------------------------------------------------------------------------------
7.1 Scaling Beyond One App
    - When to monorepo                        - Multiple apps sharing UI/types/config, or a design system consumed by several products.
    - Tooling                                    - Turborepo/Nx for task orchestration + remote build caching; pnpm/yarn workspaces for dependency linking.
    - Shared packages layout                       - packages/ui, packages/config (eslint/tsconfig), packages/types as internally-versioned or workspace-linked packages.
    - Build caching                                  - Content-hash-based task caching so unaffected packages skip rebuild/retest in CI.


--------------------------------------------------------------------------------
SECTION 8: ENVIRONMENT & CONFIGURATION MANAGEMENT
--------------------------------------------------------------------------------
8.1 Config Across Environments
    - Build-time vs runtime config              - Bundler env vars (baked in at build) vs runtime-injected config (window.__ENV__) for a single build promoted across environments.
    - Secrets handling                             - Never in client bundles; anything shipped to the browser is public - proxy secret-requiring calls through a backend/BFF.
    - Feature flags                                  - LaunchDarkly/GrowthBook-style gating for progressive rollout, kill switches, and A/B testing independent of deploys.
    - Per-environment API base URLs, staging vs prod parity considerations.


--------------------------------------------------------------------------------
SECTION 9: AUTHENTICATION & AUTHORIZATION ARCHITECTURE
--------------------------------------------------------------------------------
9.1 Real-World Auth Concerns
    - Token storage tradeoffs                  - httpOnly cookies (XSS-safe, CSRF-prone) vs localStorage/memory (XSS-prone, no CSRF) - pick based on threat model.
    - Refresh token flow                          - Silent refresh, token rotation, and handling concurrent requests during a refresh.
    - Role/permission-based UI gating                - Hiding vs disabling vs 403-routing for unauthorized actions; never trusting client-side gating alone.
    - SSR-aware session handling                       - Reading auth state on the server (cookies) vs client (hydration mismatch risk if they disagree).


--------------------------------------------------------------------------------
SECTION 10: ERROR HANDLING & RESILIENCE
--------------------------------------------------------------------------------
10.1 Designing for Failure
    - Error boundary hierarchy                 - Route-level vs section-level boundaries so one broken widget doesn't blank the whole page.
    - Fallback UI strategy                        - Skeletons vs spinners vs stale-while-revalidate content for perceived reliability.
    - Retry/backoff patterns                        - Automatic retry for transient network failures vs surfacing a manual retry action to the user.
    - Offline handling                                - Service worker caching, optimistic queues for actions taken while offline.


--------------------------------------------------------------------------------
SECTION 11: OBSERVABILITY & MONITORING
--------------------------------------------------------------------------------
11.1 Knowing What's Happening in Production
    - RUM (Real User Monitoring)               - Web Vitals + custom timing marks tied to real user sessions, not just synthetic tests.
    - Error tracking                              - Sentry-style capture with source maps, release tagging, and user/session context attached.
    - Structured client logging                     - Consistent event shape so logs are queryable, not just console.log noise.
    - Analytics/event architecture                    - A typed event schema (event name + payload contract) so product analytics don't rot into inconsistent ad-hoc calls.


--------------------------------------------------------------------------------
SECTION 12: CI/CD PIPELINE DESIGN
--------------------------------------------------------------------------------
12.1 Shipping Safely
    - Pipeline stages                          - lint -> typecheck -> unit/component tests -> build -> E2E -> deploy, fail fast ordering (cheapest checks first).
    - Preview deployments per PR                  - Ephemeral environments for reviewer/stakeholder verification before merge.
    - Performance gating                            - Lighthouse CI / bundle-size checks blocking merges on regression.
    - Progressive rollout                             - Canary releases, staged percentage rollouts, and fast rollback paths tied to monitoring alerts.


--------------------------------------------------------------------------------
SECTION 13: TESTING STRATEGY
--------------------------------------------------------------------------------
13.1 The Real-World Testing Pyramid
    - Unit tests (many, fast)                 - Pure functions, utilities, reducers - cheapest to write and maintain.
    - Component tests (Jest/RTL, moderate)       - Behavior of individual components in isolation, the highest-leverage layer for UI regressions.
    - Integration tests (fewer)                    - Multiple components + real state management wired together, mocked network boundary.
    - E2E tests (Playwright, fewest)                 - Critical user journeys only (login, checkout) - expensive to run/maintain, reserved for what truly must never break.
    - Contract testing                                 - Verifying frontend assumptions about API shape stay in sync with the backend (via generated types or Pact-style contracts).


--------------------------------------------------------------------------------
SECTION 14: PERFORMANCE & SCALABILITY PATTERNS
--------------------------------------------------------------------------------
14.1 Architecting for Scale
    - Code-splitting boundaries                - Route-level as the default, component-level for genuinely heavy/rare features (charts, editors).
    - Micro-frontends                             - When multiple independent teams truly need independent deploy cadences - not a default choice; adds real runtime/tooling overhead (see Module Federation).
    - Rendering strategy decision framework          - Static (marketing pages) vs ISR (semi-dynamic content) vs SSR (personalized/authenticated) vs CSR (highly interactive apps behind auth).
    - Caching layers                                   - Browser cache -> CDN edge cache -> server data cache -> database - knowing which layer actually needs invalidating on a change.


--------------------------------------------------------------------------------
SECTION 15: TEAM & COLLABORATION PRACTICES
--------------------------------------------------------------------------------
15.1 Process as Architecture
    - Design system governance                 - Who owns component API changes, versioning/deprecation policy for shared UI packages.
    - PR review conventions                       - What blocks a merge (tests, types, a11y) vs what's a follow-up comment.
    - Documentation-as-code                          - Storybook + MDX docs living next to components, README per package, kept in the same PR as the change.
    - ADRs (Architecture Decision Records)             - Short, dated documents capturing why a non-obvious technical choice was made, so it isn't re-litigated or silently reversed later.
